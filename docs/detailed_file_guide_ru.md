# Подробный разбор файлов проекта

Этот документ нужен как карта проекта: по нему можно быстро понять, какие файлы есть в системе, зачем нужен каждый из них, на каком этапе он подключается и с чем взаимодействует.

Документ описывает именно рабочие исходники и важные проектные файлы. Временные папки и артефакты вроде `outputs/`, `tmp_check/`, `__pycache__/`, промежуточных тестовых JSON и отладочных результатов сюда сознательно не включены как основные элементы архитектуры.

---

## 1. Общая логика проекта

Проект представляет собой веб-сервис на Flask для проверки оформления DOCX-документов по нормативным требованиям.

В системе есть три большие линии работы:

1. Проверка документа по уже готовому профилю правил.
2. Извлечение правил из методички или ГОСТа.
3. Формирование результатов проверки: HTML-отчёта, рецензированного DOCX и исправленного DOCX.

Поэтому файлы в проекте естественно делятся на группы:

- запуск и конфигурация;
- веб-слой;
- модели данных;
- парсинг DOCX;
- извлечение правил из методички;
- проверяющие модули;
- сервисы формирования результатов;
- шаблоны интерфейса и статические файлы;
- встроенные профили и вспомогательные скрипты.

## 2. Корневые файлы проекта

### `run.py`

Главный файл запуска веб-приложения.

Что делает:

- создаёт Flask-приложение через фабрику из `app/__init__.py`;
- запускает локальный сервер;
- используется в обычном режиме работы, когда пользователь открывает интерфейс в браузере.

Когда подключается:

- в самом начале, при старте приложения.

Почему нужен отдельно:

- чтобы точка входа в проект была простой и понятной;
- чтобы логика инициализации не смешивалась с маршрутизацией и бизнес-логикой.

---

### `run_check.py`

Служебный скрипт для запуска проверки без браузера.

Что делает:

- позволяет прогнать проверку документа напрямую из консоли;
- полезен для отладки, быстрых прогонов и локального тестирования без веб-интерфейса.

Когда используется:

- при ручной проверке кода разработчиком;
- в отладочных сценариях.

---

### `check_profile.py`

Служебный файл для проверки корректности JSON-профиля.

Что делает:

- загружает профиль;
- валидирует его через Pydantic-модели;
- помогает быстро понять, не сломан ли JSON по структуре.

Почему полезен:

- профиль правил — центральная сущность системы;
- если профиль некорректен, вся проверка дальше теряет смысл.

## 4. Файлы верхнего уровня внутри `app/`

### `app/__init__.py`

Файл инициализации Flask-приложения.

Это один из самых важных инфраструктурных файлов проекта.

Что делает:

- создаёт Flask-приложение;
- задаёт конфигурацию путей;
- регистрирует blueprint с маршрутами;
- создаёт рабочие директории;
- запускает очистку временных файлов.

Что именно настраивается здесь:

- папка загрузок `uploads/`;
- папка результатов `outputs/`;
- путь к встроенному профилю;
- общие параметры приложения.

Почему это важно:

- все остальные модули потом опираются на эти пути;
- здесь определяется, где временно живут загруженные документы, куда складываются результаты и какой встроенный профиль считается базовым.

Также здесь находится логика очистки старых временных файлов, чтобы приложение не накапливало мусор бесконечно.

---

### `app/routes.py`

Главный веб-маршрутизатор проекта.

Этот файл связывает интерфейс и внутреннюю логику системы.

Что делает:

- принимает HTTP-запросы от пользователя;
- сохраняет загруженные файлы;
- запускает проверку документа;
- запускает извлечение правил из методички;
- обрабатывает подтверждение кандидатов правил;
- отдаёт пользователю отчёты и DOCX-результаты.

Основные сценарии, которые отсюда запускаются:

1. Загрузка документа на проверку.
2. Загрузка JSON-профиля.
3. Выбор встроенного профиля.
4. Загрузка методички и запуск конвейера извлечения правил.
5. Сохранение подтверждённого извлечённого профиля.
6. Скачивание или открытие результатов.

Почему файл важен:

- это точка входа для почти всех пользовательских действий;
- через него веб-интерфейс подключается к бизнес-логике.

## 5. Папка `app/models/` — модели данных

Эти файлы описывают, **в каком виде данные живут внутри системы**.

Очень важно понимать: модель в проекте — это не “алгоритм”, а строгая структура данных.

Модели нужны, чтобы разные части системы говорили на одном языке:

- парсер возвращает документ не как случайный словарь, а как `ParsedDocxDocument`;
- профиль правил хранится не как произвольный JSON, а как `Profile` и `Rule`;
- нарушения имеют единую форму `Violation`.

Это сильно упрощает архитектуру и уменьшает количество ошибок.

---

### `app/models/document.py`

Одна из ключевых моделей проекта.

Этот файл описывает внутреннюю модель разобранного DOCX-документа.

Главные классы:

- `ParagraphType` — тип абзаца;
- `TextRunData` — один текстовый фрагмент внутри абзаца;
- `ParagraphData` — один абзац;
- `ImageData` — одно изображение;
- `TableData` — одна таблица;
- `SectionData` — одна секция документа;
- `ParsedDocxDocument` — весь документ после парсинга.

Зачем это нужно:

- парсер извлекает из DOCX множество разнородных данных;
- чекерам нужен единый формат, в котором можно обращаться к абзацам, таблицам, изображениям и секциям;
- модели превращают сложный DOCX в понятную внутреннюю структуру.

Например:

- `ParagraphData` хранит текст, стиль, выравнивание, интервалы, признаки заголовка, маркеры списка, параметры формулы;
- `TableData` хранит структуру таблицы, заголовок, параметры границ, признаки повторяющейся головки и текст ячеек;
- `SectionData` хранит поля страницы, колонтитулы и нумерацию.

Это файл, на котором буквально держится вся последующая проверка.

---

### `app/models/profile.py`

Описывает структуру профиля проверки.

Главные сущности:

- `Rule` — одно правило;
- `Profile` — весь профиль;
- перечисления категорий, операторов, модальности и происхождения правила.

Что хранится в одном правиле:

- `target` — к какому объекту относится правило;
- `parameter` — какой параметр проверяется;
- `operator` — как сравнивать;
- `value` — требуемое значение;
- `modality` — обязательное, рекомендательное или разрешающее;
- `origin` — встроенное правило или извлечённое;
- описание и источник.

Этот файл важен тем, что именно он делает JSON-профиль формализованным и пригодным для автоматической проверки.

---

### `app/models/violation.py`

Описывает одно найденное нарушение.

Что хранит:

- идентификатор правила;
- параметр;
- целевой объект;
- место нарушения;
- ожидаемое значение;
- найденное значение;
- сообщение;
- серьёзность;
- тип нарушения.

Зачем нужен:

- все чекеры возвращают результаты именно в этом формате;
- дальше один и тот же `Violation` используется в HTML-отчёте, комментариях Word и автоисправлении.

То есть этот файл унифицирует результаты проверки.

---

### `app/models/check_result.py`

Модель итогового результата работы сервиса проверки.

Обычно содержит:

- путь к HTML-отчёту;
- путь к исправленному документу;
- путь к документу с комментариями;
- список нарушений и производную служебную информацию.

Зачем нужен:

- чтобы `CheckService` возвращал не россыпь случайных значений, а единый объект результата.

## 6. Папка `app/parsers/`

Здесь лежит модуль, который превращает DOCX во внутреннюю модель документа.

---

### `app/parsers/docx_parser.py`

Один из самых больших и самых важных файлов проекта.

Его задача:

- открыть DOCX;
- извлечь структуру документа;
- вычислить фактические параметры оформления;
- классифицировать элементы;
- вернуть объект `ParsedDocxDocument`.

Что именно делает этот файл:

1. Проверяет, что файл существует и это `.docx`.
2. Открывает документ через `python-docx`.
3. Проходит по абзацам основного текста.
4. Для каждого абзаца:
   - извлекает текст;
   - ищет разрывы;
   - ищет формулы;
   - ищет маркеры списка;
   - ищет изображения;
   - вычисляет шрифт, размер, выравнивание, интервалы и отступы.
5. Отдельно разбирает `run`-ы внутри абзаца.
6. Передаёт собранный абзац в классификатор.
7. Помечает титульную часть.
8. Отдельно разбирает изображения.
9. Отдельно разбирает таблицы и абзацы внутри ячеек.
10. Отдельно читает сноски и настройки сносок напрямую из XML внутри DOCX.
11. Отдельно разбирает секции, поля, колонтитулы и нумерацию.
12. Возвращает `ParsedDocxDocument`.

Почему этот файл большой:

- DOCX — сложный формат;
- многие параметры Word заданы не напрямую, а через наследование стилей;
- для реальной проверки недостаточно просто прочитать текст.

Особенно важные вещи в этом файле:

- вычисление фактического значения параметров по цепочке наследования;
- различение обычных абзацев и текста в таблицах;
- чтение нумерации страниц через XML-поля Word;
- связывание рисунков и таблиц с окружающими абзацами;
- подготовка данных для чекеров в одном формате.

Это фундамент всей системы проверки.

## 7. Папка `app/services/`

Здесь лежит слой прикладной логики.  
Если парсер просто разбирает документ, то сервисы уже координируют проверку, группировку, рецензирование и автоисправление.

---

### `app/services/check_service.py`

Главный координатор проверки.

Это центральный сервис проекта.

Что делает:

1. Загружает профиль.
2. Запускает `DocxParser`.
3. Передаёт результат в чекеры.
4. Собирает все нарушения.
5. Фильтрует шумные и лишние сообщения.
6. Строит HTML-отчёт.
7. Создаёт рецензированный DOCX.
8. Создаёт исправленный DOCX.

Почему это не делается в `routes.py`:

- маршрут должен только принять запрос и вернуть ответ;
- бизнес-логика проверки не должна быть размазана по веб-слою.

Особенно важные обязанности этого файла:

- управление полным циклом проверки;
- подавление шумных проверок;
- фильтрация титульного листа и начальных страниц;
- объединение результатов модулей в единый поток.

---

### `app/services/paragraph_classifier.py`

Логический классификатор абзацев.

Он используется внутри парсера, но вынесен отдельно, потому что это самостоятельная логика.

Что делает:

- определяет, является ли абзац заголовком;
- распознаёт структурные заголовки;
- распознаёт подписи рисунков и таблиц;
- распознаёт списки;
- помечает пустые абзацы;
- присваивает абзацу тип `ParagraphType`.

Что использует:

- регулярные выражения;
- словари структурных заголовков;
- признаки Word-стиля;
- эвристики длины и формы текста.

Зачем выносить в отдельный файл:

- классификация — отдельная большая задача;
- она используется парсером и влияет на все последующие проверки;
- этот код удобнее поддерживать отдельно от чисто технического извлечения параметров.

---

### `app/services/parameter_registry.py`

Реестр параметров и их человекочитаемых представлений.

Этот файл нужен для того, чтобы внутренние технические имена вроде `font_size`, `keep_with_next` или `page_break_before` превращались в понятные подписи для интерфейса и отчёта.

Что делает:

- хранит словари соответствий;
- возвращает русские названия параметров;
- помогает формировать понятные сообщения.

Без него отчёт был бы слишком техническим.

---

### `app/services/profile_utils.py`

Вспомогательная логика работы с профилями.

Задачи такого файла обычно связаны с:

- поиском нужных правил;
- группировкой правил;
- фильтрацией правил по объектам;
- подготовкой правил для автокоррекции и проверки.

Это сервисный слой вокруг профиля как структуры данных.

---

### `app/services/violation_grouping.py`

Модуль группировки нарушений.

Зачем он нужен:

- один документ может содержать десятки и сотни нарушений;
- показывать их просто плоским списком неудобно;
- системе нужен слой, который соберёт нарушения в понятные группы.

Что делает:

- группирует нарушения по разделам, правилам и типам;
- подготавливает структуру для HTML-отчёта и экранного отображения.

---

### `app/services/review_docx_service.py`

Модуль формирования DOCX с комментариями Word.

Это очень важный и технически интересный файл.

Что делает:

- создаёт копию исходного документа;
- добавляет комментарии Word в места нарушений;
- пишет данные напрямую в XML DOCX-пакета.

Почему это не делается простым API python-docx:

- библиотека не даёт удобной высокоуровневой поддержки комментариев Word;
- поэтому комментарии создаются через работу с XML внутри DOCX-архива.

Что делает внутри:

- формирует текст комментария;
- группирует связанные нарушения;
- создаёт элементы comments.xml;
- вставляет ссылки комментариев в основной текст документа;
- обновляет связи и content types.

Это файл, который отвечает за “рецензированный документ”.

---

### `app/services/autocorrect_service.py`

Модуль автоматического исправления.

Что делает:

- создаёт копию документа;
- применяет безопасные формальные исправления;
- не меняет смысл текста.

Что обычно исправляет:

- шрифты;
- размеры;
- интервалы;
- отступы;
- выравнивание;
- параметры заголовков;
- часть параметров страниц;
- часть типографических нарушений.

Почему он вынесен отдельно:

- автокоррекция — это не проверка, а изменение документа;
- для неё нужен свой отдельный контролируемый слой логики.

Это один из самых чувствительных модулей: здесь любое неверное действие может испортить документ, поэтому архитектурно он отделён от проверки.

---

## 8. Папка `app/checkers/`

Это набор модулей, которые уже получают:

- разобранный документ;
- профиль правил;

и возвращают нарушения.

Именно они отвечают за собственно нормоконтроль.

---

### `app/checkers/format_checker.py`

Главный модуль проверок форматирования.

Что проверяет:

- параметры основного текста;
- параметры заголовков;
- параметры страницы;
- подписи рисунков;
- названия таблиц;
- оформление таблиц;
- параметры абзацев и частей документа.

Это самый большой по объёму тип проверок, потому что большинство формализуемых требований относится именно к форматированию.

---

### `app/checkers/typography_checker.py`

Модуль типографических проверок.

Что проверяет:

- пробелы;
- двойные пробелы;
- неразрывные пробелы;
- тире и дефисы;
- кавычки;
- единицы измерения;
- оформление некоторых устойчивых текстовых конструкций.

Отличие от `format_checker`:

- `format_checker` смотрит в первую очередь на параметры Word-оформления;
- `typography_checker` анализирует уже сам текст и его символьную форму.

---

### `app/checkers/structure_checker.py`

Модуль структурных проверок.

Что проверяет:

- наличие обязательных разделов;
- состав введения;
- состав заключения;
- соответствие содержания;
- часть правил по списку источников;
- скрытую нумерацию начальных страниц;
- другие требования, связанные с логической структурой документа.

Он нужен потому, что структура — это отдельный класс требований, который плохо укладывается в обычные “параметр = значение”.

---

### `app/checkers/consistency_checker.py`

Модуль проверки единообразия.

Что делает:

- ищет, одинаково ли оформлен основной текст;
- анализирует доминирующие параметры;
- выявляет выбросы и локальные отклонения.

Пример:

- если большая часть документа набрана 14 пт, а один абзац 12 пт, это нарушение единообразия.

Этот чекер особенно важен там, где правило не задано жёстким числом в профиле, а логика строится вокруг повторяемости и доминанты.

---

### `app/checkers/section_consistency_checker.py`

Проверка единообразия между секциями документа.

Что делает:

- сравнивает параметры страниц и секций;
- ищет различия полей и других секционных параметров;
- помогает выявить случайные сбои в структуре большого документа.

Он отделён от обычного `consistency_checker`, потому что уровень анализа другой: не абзацный, а секционный.

---

### `app/checkers/linguistic_checker.py`

Лингвистический модуль.

Что проверяет:

- некоторые языковые требования;
- запрещённые конструкции;
- формы глаголов;
- местоимения;
- повелительное наклонение;
- часть требований к формулировкам задач и текста.

Что использует:

- `natasha`;
- словари маркеров;
- эвристики.

Это модуль для частично формализуемых требований: там, где одного форматирования уже недостаточно, но смысловой анализ ещё можно ограниченно автоматизировать.

## 9. Папка `app/extraction/` — конвейер извлечения правил

Эта папка отвечает за новую ключевую функцию системы: получение профиля правил не вручную, а из загруженного нормативного документа.

Здесь происходит путь:

`методичка / ГОСТ -> кандидаты правил -> подтверждение -> JSON-профиль`

---

### `app/extraction/__init__.py`

Технический файл инициализации пакета.

Нужен для того, чтобы папка `extraction/` была полноценным Python-пакетом.

---

### `app/extraction/models.py`

Модели данных конвейера извлечения.

Главные сущности:

- `NormativeSection`
- `NormativeFragment`
- `ExtractedRuleCandidate`

Зачем нужны:

- сегментация и извлечение не работают напрямую со строками;
- каждому этапу нужен свой формальный тип данных;
- кандидат правила должен быть отдельной сущностью, потому что найденное правило ещё не равно подтверждённому правилу профиля.

Особенно важен `ExtractedRuleCandidate`:

- в нём хранится параметр;
- значение;
- модальность;
- уверенность;
- статус;
- исходный фрагмент методички;
- пояснение, почему кандидат принят, спорный или неподдерживаемый.

---

### `app/extraction/patterns.py`

Файл шаблонов и регулярных выражений.

Что хранит:

- whitelist поддерживаемых параметров;
- набор extractors;
- ключевые слова;
- регулярные выражения для поиска значений;
- словари нормализации значений.

Почему это отдельный файл:

- шаблоны извлечения — это данные и правила распознавания, а не управляющая логика;
- их удобнее расширять отдельно от кода извлечения.

Это один из ключевых файлов, которые определяют, **какие именно требования система вообще умеет автоматически извлекать**.

---

### `app/extraction/segmenter.py`

Этап сегментации нормативного документа.

Что делает:

- читает DOCX или PDF;
- разбивает документ на секции;
- отбрасывает вводный шум до начала нормативной части;
- выделяет фрагменты внутри секций;
- отделяет требования от примеров и примечаний.

Почему это важно:

- без сегментации извлечение шло бы по сплошному тексту и постоянно путало бы реальные требования с пояснениями и примерами.

---

### `app/extraction/statement_builder.py`

Модуль построения атомарных утверждений.

Его роль:

- взять крупный фрагмент текста;
- разбить его на более мелкие смысловые утверждения;
- подготовить материал для дальнейшего извлечения правил.

Это позволяет переходить от больших абзацев методички к более удобным единицам анализа.

---

### `app/extraction/parameter_extractor.py`

Основной извлекатель параметров.

Именно здесь шаблоны и регулярные выражения применяются к тексту методички.

Что делает:

- берёт только фрагменты-требования;
- подбирает подходящий extractor;
- проверяет ключевые слова;
- применяет регулярное выражение;
- преобразует найденное значение;
- пытается определить target по контексту;
- создаёт `ExtractedRuleCandidate`.

Почему сначала ключевые слова, а потом регулярка:

- это уменьшает ложные срабатывания;
- число “14” может означать кегль, номер рисунка, номер раздела или что-то ещё;
- сначала система должна понять, что речь вообще, например, о шрифте.

Это один из центральных файлов всего конвейера.

---

### `app/extraction/modality_detector.py`

Модуль определения модальности требования.

Что делает:

- ищет слова-маркеры обязательности;
- различает “должен”, “рекомендуется”, “допускается”;
- определяет, является правило обязательным, рекомендательным или разрешающим.

Зачем нужен:

- не все требования в методичке имеют одинаковую силу;
- это должно попасть в профиль.

---

### `app/extraction/structure_extractor.py`

Отдельный извлекатель структурных требований.

Почему он нужен отдельно:

- не все правила методички — это обычные числовые параметры вроде “14 пт”;
- есть структурные требования: состав введения, содержание, порядок разделов, минимальное число источников.

Этот файл отвечает именно за поиск таких правил.

---

### `app/extraction/verifier.py`

Модуль перепроверки кандидатов правил.

Что делает:

- проводит sanity-check значений;
- находит конфликты;
- понижает уверенность при спорных признаках;
- назначает статус кандидата.

Зачем нужен:

- конвейер не должен слепо превращать каждую найденную цифру в готовое правило;
- нужен отдельный этап самопроверки извлечения.

---

### `app/extraction/presentation.py`

Слой представления кандидатов правил.

Что делает:

- превращает технические кандидаты в удобный для интерфейса вид;
- группирует и форматирует их для страницы подтверждения правил.

Это важный мост между внутренними моделями извлечения и пользовательским интерфейсом.

---

### `app/extraction/pipeline.py`

Главный оркестратор конвейера извлечения.

Что делает:

1. Запускает сегментацию.
2. Разбивает секции на фрагменты.
3. Строит утверждения.
4. Извлекает параметрические кандидаты.
5. Извлекает структурные кандидаты.
6. Определяет модальность.
7. Перепроверяет кандидатов.
8. Возвращает итоговый список кандидатов.

Также здесь находится функция построения подтверждённого профиля из выбранных кандидатов.

Это для извлечения правил то же самое, чем `check_service.py` является для проверки документа.

## 17. Коротко о связях между файлами

Если упростить связи до одной цепочки, получается так:

1. `run.py` запускает приложение.
2. `app/__init__.py` создаёт и настраивает Flask.
3. `app/routes.py` принимает документ и профиль.
4. `app/services/check_service.py` координирует проверку.
5. `app/parsers/docx_parser.py` разбирает DOCX.
6. `app/models/document.py` задаёт форму внутренней модели.
7. `app/checkers/*` проверяют документ по профилю.
8. `app/models/violation.py` задаёт единый формат нарушений.
9. `app/reports/html_report.py`, `app/services/review_docx_service.py`, `app/services/autocorrect_service.py` строят результаты.

Для извлечения правил цепочка другая:

1. `app/routes.py` принимает методичку.
2. `app/extraction/pipeline.py` запускает конвейер.
3. `segmenter.py`, `statement_builder.py`, `parameter_extractor.py`, `structure_extractor.py`, `modality_detector.py`, `verifier.py` по шагам извлекают кандидатов.
4. `models.py` задаёт формат кандидатов.
5. `presentation.py` подготавливает их для интерфейса.
6. подтверждённые кандидаты превращаются в JSON-профиль.

## 18. Для чего нужен этот документ на практике

Этот файл удобно использовать в трёх ситуациях:

1. Перед защитой, чтобы быстро восстановить в голове структуру проекта.
2. Во время ответов на вопросы комиссии, когда нужно объяснить, какой файл за что отвечает.
3. При дальнейшей доработке проекта, чтобы не тратить время на повторное ручное ориентирование в кодовой базе.

Если нужно, следующим шагом можно сделать ещё более глубокую версию:  
отдельный документ, где уже не просто описано назначение файлов, а по каждому из ключевых файлов разобраны **главные функции внутри него, порядок их вызова и поток данных между ними**.
